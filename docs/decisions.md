# 判断記録（Decision Log）

資料とタスク指示が食い違った箇所、資料に記載がなく判断した箇所を記録する。形式は「判断 / 理由 / 代替案」。

## D-01 トークンは design-tokens 2.0.1 の値を `src/tokens/` に転記する

- 判断: 公式 npm パッケージ（`@digital-go-jp/design-tokens`、`@digital-go-jp/tailwind-theme-plugin`）を依存に追加せず、値を `src/tokens/primitives.css` と `src/tokens/typography.css` に転記する（MIT ライセンス、出典を明記）。
- 理由: Tailwind v4 の `@theme` で `--color-*: initial` により既定パレットを無効化したい。プラグインの `@import` と初期化の順序を制御できず、既定色が残ると「トークン以外の色が使えない」保証が崩れる。依存を最小限にする指示にも合う。
- 代替案: `@import "@digital-go-jp/tailwind-theme-plugin/v4"` を使う（公式更新への追従が容易だが、既定パレットの無効化と命名の一貫性が保てない）。

## D-02 フォントは `@fontsource-variable/noto-sans-jp` でセルフホストする

- 判断: Noto Sans JP（可変フォント）を npm パッケージから読み込む。
- 理由: DADS はフォントとして Noto Sans JP を指定し、Google Fonts の例を示している。ただし行政の管理画面テンプレートでは外部 CDN への接続（利用者の IP が外部に渡る）を避けたい。ユニコード範囲ごとに分割された woff2 のため、必要な部分しか読み込まれない。
- 代替案: Google Fonts の `<link>`（ネットワーク依存）、システムフォントのみ（DADS の指定から外れる）。

## D-03 グラフライブラリは Recharts 1 つに絞り、ラッパー経由で使う

- 判断: `recharts` を採用し、`src/components/charts/` のラッパー（ChartFrame + LineChart / BarChart / AreaChart / DonutChart）からのみ使う。
- 理由: SVG ベースで CSS 変数による配色・ARIA 属性の付与・データテーブル切り替えの実装が容易。React 19 対応済み。
- 代替案: Chart.js（canvas のため DOM で代替手段を作る必要がある）、D3 直書き（実装コストが高い）。

## D-04 散布図は実装しない

- 判断: 散布図は「不要」とする。
- 理由: ダッシュボードガイドブックが提供・推奨するグラフは指標、折れ線、棒（集合・積み上げ）、積み上げ面、表、円（ドーナツ）、複合グラフで、散布図は含まれない。タスク指示も「ガイドブックで推奨・許容されるものに限る」としている。
- 代替案: 2 変数の関係を見せたい場合は表（データテーブル）を使う。

## D-05 ブレークポイントは Tailwind 既定（md = 768px を DADS の 1 ブレークポイントとして扱う）

- 判断: `sm 640 / md 768 / lg 1024 / xl 1280` を維持し、「モバイルとデスクトップの切り替え」は常に `md` で行う。
- 理由: DADS は 768px の 1 ブレークポイントを想定しているが、サイドバー付き管理画面ではサイドバーの常時表示（lg 以上）や KPI の 4 列化（xl）など、追加の段階が必要。
- 代替案: `md` のみに限定する（広い画面で情報密度を上げられない）。

## D-06 本文 16px、密度の高い表・補足は 14px（Dense）まで。14px 未満は使わない

- 判断: Tailwind 既定の `text-xs`（12px）/ `text-sm`（14px）を無効化し、DADS のサイズ（14 / 16 / 17 / 18 / 20 / 22 / 24 / 26 / 28 / 32 / 36 / 45 / 48 / 57 / 64）だけを `text-*` に定義する。テキストスタイル（`text-std-16N-170` 等）も用意する。
- 理由: DADS は本文・UI の基準を 16px 以上とし、14px は限定用途、14px 未満は原則不可としている。
- 代替案: 既存の 11〜13px を残す（DADS 非準拠）。

## D-07 管理画面の面構成（地と面）

- 判断: アプリ全体の地（canvas）を `solid-gray-50`（#f2f2f2）、カード等の面（surface）を白にする。カードは `solid-gray-420` の 1px 枠線で区切り、影は使わない（ホバー時も使わない）。
- 理由: DADS は「管理画面では高さレベルの高低差を狭くする」「影でコントラストを確保しない」としている。ガイドブックの背景 Standard（#F8F8FB）は DADS パレット外のため、最も近いニュートラルを採用。
- 代替案: 全面白 + ディバイダーのみ（面の区切りが弱い）。

## D-08 ボタンの `disabled` は Props として提供するが、ページ例では使わない

- 判断: Button は `disabled` / `loading` を受け付ける（テンプレートの汎用性のため）。ページ例の送信ボタンは無効化せず、未入力時はエラーテキストで案内する。
- 理由: DADS は `disabled` を原則使わない（Tab で到達できない）とし、どうしても使う場合は近くに理由を表示することを求めている。
- 代替案: `disabled` を Props から外す（他プロジェクトで必要になりがち）。

## D-09 エラーテキストに `aria-live` / `role="alert"` を付けない

- 判断: フォームのエラーは静的テキストとして表示し、`aria-describedby` で入力に関連付ける。送信時のまとめ（エラーサマリー）はノティフィケーションバナー（error）で表示し、送信後にそこへフォーカスを移す。
- 理由: DADS インプットテキスト（アクセシビリティ）の規定。
- 代替案: `role="alert"`（読み上げの割り込みが起こる）。

## D-10 トースト通知は DADS に該当コンポーネントがないため、ノティフィケーションバナーの縮小版として設計する

- 判断: 画面右上（モバイルは下部）に固定表示、`role="status"`（`aria-live="polite"`）、success / error / info の意味色、閉じるボタン付き、8 秒で自動消去（ホバー・フォーカス中は停止）。
- 理由: 操作完了の軽い通知は管理画面で必須。DADS のセマンティックカラーと「固定表示には閉じるボタンを必ず付ける」規定に従う。
- 代替案: すべてバナーで表示する（画面がうるさくなる）。

## D-11 ツールチップ・ポップオーバー・コマンドパレット・スケルトン・タイムライン等は DADS にないため APG に従って設計する

- 判断: WAI-ARIA Authoring Practices のパターン（Tooltip、Dialog、Combobox など）に従い、見た目は DADS のトークン（枠線 gray-420、elevation-1、角丸 8px、フォーカスリング）で統一する。
- 理由: 資料に記載がない部分は DADS の原則（アクセシビリティ、一貫性）から判断する。

## D-12 データ可視化パレット

- 判断: ガイドブック「Blue」パレットから、白背景に対し 3:1 以上を満たす色を系列色に採用する。
  - 系列: 1 = Blue 900 #0017c1、2 = Yellow 800 #a58000、3 = Blue 600 #3460fb、4 = Solid Gray 600 #666666、5 = Blue 1200 #000060
  - 単一色相（順序あり）: Blue 1200 / 900 / 600 / 400 / 200（400 以下は 3:1 未満のため値ラベルを必ず併記）
  - 増減: 増加 Blue 600 #3460fb（文字は Blue 800 #0031d8）、減少 Red 600 #fe3939（文字は Red 900 #ce0000）。矢印アイコンと符号を併記し色だけに依存しない
  - 目標・比較線: Solid Gray 800 の破線、グリッド: Solid Gray 200、軸: Solid Gray 600
- 理由: 色数を 5 色以内に抑え、色覚多様性（青 / 黄 / グレーは識別しやすい）とコントラスト要件を両立する。

## D-13 作業用の文書は Git に含めず、完了後に残す文書だけをコミットする

- 判断: 作業中は `docs/*.md` を `.gitignore` の対象にした（利用者の指示）。完了後、作業用の文書（進捗 `PROGRESS.md`、作り直し前の現状調査、DADS の調査メモ）は削除し、使う人の役に立つ文書（`docs/decisions.md`・`docs/tokens.md`・`docs/chart-guide.md`）だけをコミットする。
- 理由: 進捗と調査メモは作業を再開するためのもので、完了後は内容がコードと README に反映済み。判断記録・トークン一覧・グラフの選び方は、ソースコードのコメントから参照しており、テンプレートを改修するときにも使う。

## D-14 ディレクトリ構成

```
src/
├── tokens/            # デザイントークン（primitives / theme / typography）とコントラスト検査
├── components/
│   ├── ui/            # 汎用 UI 部品（1 コンポーネント = 1 ファイル + テスト）
│   └── charts/        # Recharts ラッパー
├── layouts/           # AppShell（サイドバー型）、TopNavLayout（上部ナビ型）
├── pages/             # ページ例（dashboard, applications, settings, auth, errors）
├── mocks/             # ダミーデータ
├── hooks/ lib/ context/ test/
```

- 理由: UI 部品・グラフ・レイアウト・ページ・モックを分離し、テンプレート利用者が差し替える単位を明確にする。

## D-15 デモは Storybook ではなくアプリ内ページ（`/components/*`）で提供する（D-16 で撤回）

- 判断: 依存を増やさず、`src/demo/*.demo.tsx` に使用例を書き、`/components` 配下のページで一覧表示する。E2E / axe の検査対象にもなる。
- 代替案: Storybook（依存が大きい）。

## D-16 コンポーネントのデモページを廃止し、ページ例 7 画面をプレビューとする

- 判断: 利用者の指示（「/components ページはいらない。プレビューの 7 画面でいい」）により、`/components` と `src/demo/` を削除する。部品の使用例はページ例（ダッシュボード・一覧・詳細・フォーム・設定・ログイン・404/500）と単体テストで示す。E2E の axe 検査は 7 画面と主要な操作状態（モーダル表示、フォームエラー、モバイル幅）を対象にする。
- 理由: 利用者がテンプレートとして見るのはページ例であり、デモページは不要と判断された。
- 影響: タスクの完了条件 3「各項目について、実装、デモ、単体テストがそろっている」の「デモ」は、利用者の指示によりページ例で代替する。PR の本文にも明記する。
- 代替案: デモページを開発者向けに残す（最初に提案したが、利用者が不要と判断）。

## D-17 地（canvas）の上の文字色を DADS より 1 段濃くする

- 判断: `text-subtle` を gray-536 → gray-600、`error` を error-1（red-800）→ error-2（red-900）、`warning` を yellow-900 → yellow-1000、`link-active` を orange-800 → orange-900 にする。
- 理由: DADS の値は白背景で 4.5:1 を満たすが、管理画面の地（gray-50 #f2f2f2）の上では 4.05〜4.33:1 になり、実ブラウザの axe で違反になった。DADS は「セマンティックカラーは色相を保てば明度を調整してよい」としている。
- 代替案: 地を白にする（面の区別がなくなる）。

## D-18 アプリケーションシェルはページ全体でスクロールする

- 判断: 本文だけを内側でスクロールさせる構造をやめ、ヘッダーとサイドバーを sticky にしてページ全体をスクロールさせる。
- 理由: 内側スクロールでは、画面外の要素（読み上げ用の隠しテキストなど）にフォーカスが当たったときに画面全体がずれる不具合が起きた（利用者の指摘）。

## D-19 グラフの目標線のラベルは凡例に出す

- 判断: 参照線のラベルをグラフの中に描かず、凡例に「破線 + ラベル」として出す（`labelPosition` を指定したときだけグラフ内に描く）。
- 理由: グラフ内の文字は系列の線と重なりやすい。ガイドブックは凡例をグラフに隣接させることを推奨している。

## D-20 作成フォームの操作ボタンは画面下部に固定しない

- 判断: ActionPanel の sticky を使わず、フォーム末尾に罫線で区切って置く。
- 理由: 固定表示はフォームの上に浮いて見え、入力欄やサポートテキストを隠した（利用者の指摘）。

## D-21 アイコン・チェックボックスなどは、隣の文字の 1 行目と上下中央でそろえる

- 判断: 文字の横に置く部品（アイコン、チェックボックス、ラジオボタン、マーカー、表のチップ・操作ボタン）は、文字と同じ 1 行分の高さの枠（`h-lh`）の中で上下中央に置く。表の中では `TableCellLine` で包む。
- 理由: ベースライン合わせ + 固定のずらし量（`mt-0.5` など）では、部品の大きさや行の高さが違う場所で 1〜3px ずれた（利用者の指摘）。この作りなら、文字が折り返しても 1 行目にそろう。
- 代替案: `items-center` で文字全体の中央にそろえる（複数行のとき 1 行目とずれる）。

## D-22 ボタンの並びは、モバイルでも DOM 順 = 見た目の順 = フォーカス順にする

- 判断: ダイアログの 2 つのボタンは、モバイルでも左がキャンセル・右が確定。ActionPanel と ButtonGroup も CSS の order や逆順（`flex-col-reverse`）を使わず、収まらないときだけ折り返す。
- 理由: モバイルで縦に積んで逆順にすると、幅がそろわず作りかけに見え（利用者の指摘）、見た目の順とフォーカス順も食い違う。
