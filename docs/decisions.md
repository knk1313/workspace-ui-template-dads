# 判断記録（Decision Log）

資料とタスク指示が食い違った箇所、資料に記載がなく判断した箇所を記録する。形式は「判断、理由、代替案」。

## D-01トークンはdesign-tokens 2.0.1の値を`src/tokens/`に転記する

- 判断：公式npmパッケージ（`@digital-go-jp/design-tokens`、`@digital-go-jp/tailwind-theme-plugin`）を依存に追加せず、値を`src/tokens/primitives.css`と`src/tokens/typography.css`に転記する（MITライセンス、出典を明記）。
- 理由：Tailwind v4の`@theme`で`--color-*：initial`により既定パレットを無効化したい。プラグインの`@import`と初期化の順序を制御できず、既定色が残ると「トークン以外の色が使えない」保証が崩れる。依存を最小限にする指示にも合う。
- 代替案：`@import "@digital-go-jp/tailwind-theme-plugin/v4"`を使う（公式更新への追従が容易だが、既定パレットの無効化と命名の一貫性が保てない）。

## D-02フォントは`@fontsource-variable/noto-sans-jp`でセルフホストする

- 判断：Noto Sans JP（可変フォント）をnpmパッケージから読み込む。
- 理由：DADSはフォントとしてNoto Sans JPを指定し、Google Fontsの例を示している。ただし行政の管理画面テンプレートでは外部CDNへの接続（利用者のIPが外部に渡る）を避けたい。ユニコード範囲ごとに分割されたwoff2のため、必要な部分しか読み込まれない。
- 代替案：Google Fontsの`<link>`（ネットワーク依存）、システムフォントのみ（DADSの指定から外れる）。

## D-03グラフライブラリはRecharts 1つに絞り、ラッパー経由で使う

- 判断：`recharts`を採用し、`src/components/charts/`のラッパー（ChartFrame + LineChart、BarChart、AreaChart、DonutChart）からのみ使う。
- 理由：SVGベースでCSS変数による配色・ARIA属性の付与・データテーブル切り替えの実装が容易。React 19対応済み。
- 代替案：Chart.js（canvasのためDOMで代替手段を作る必要がある）、D3直書き（実装コストが高い）。

## D-04散布図は実装しない

- 判断：散布図は「不要」とする。
- 理由：ダッシュボードガイドブックが提供・推奨するグラフは指標、折れ線、棒（集合・積み上げ）、積み上げ面、表、円（ドーナツ）、複合グラフで、散布図は含まれない。タスク指示も「ガイドブックで推奨・許容されるものに限る」としている。
- 代替案：2変数の関係を見せたい場合は表（データテーブル）を使う。

## D-05ブレークポイントはTailwind既定（md = 768pxをDADSの1ブレークポイントとして扱う）

- 判断：`sm 640、md 768、lg 1024、xl 1280`を維持し、「モバイルとデスクトップの切り替え」は常に`md`で行う。
- 理由：DADSは768pxの1ブレークポイントを想定しているが、サイドバー付き管理画面ではサイドバーの常時表示（lg以上）やKPIの4列化（xl）など、追加の段階が必要。
- 代替案：`md`のみに限定する（広い画面で情報密度を上げられない）。

## D-06本文16px、密度の高い表・補足は14px（Dense）まで。14px未満は使わない

- 判断：Tailwind既定の`text-xs`（12px）/ `text-sm`（14px）を無効化し、DADSのサイズ（14、16、17、18、20、22、24、26、28、32、36、45、48、57、64）だけを`text-*`に定義する。テキストスタイル（`text-std-16N-170`等）も用意する。
- 理由：DADSは本文・UIの基準を16px以上とし、14pxは限定用途、14px未満は原則不可としている。
- 代替案：既存の11〜13pxを残す（DADS非準拠）。

## D-07管理画面の面構成（地と面）

- 判断：アプリ全体の地（canvas）を`solid-gray-50`（#f2f2f2）、カード等の面（surface）を白にする。カードは`solid-gray-420`の1px枠線で区切り、影は使わない（ホバー時も使わない）。
- 理由：DADSは「管理画面では高さレベルの高低差を狭くする」「影でコントラストを確保しない」としている。ガイドブックの背景Standard（#F8F8FB）はDADSパレット外のため、最も近いニュートラルを採用。
- 代替案：全面白 + ディバイダーのみ（面の区切りが弱い）。

## D-08ボタンの`disabled`はPropsとして提供するが、ページ例では使わない

- 判断：Buttonは`disabled`、`loading`を受け付ける（テンプレートの汎用性のため）。ページ例の送信ボタンは無効化せず、未入力時はエラーテキストで案内する。
- 理由：DADSは`disabled`を原則使わない（Tabで到達できない）とし、どうしても使う場合は近くに理由を表示することを求めている。
- 代替案：`disabled`をPropsから外す（他プロジェクトで必要になりがち）。

## D-09エラーテキストに`aria-live`、`role="alert"`を付けない

- 判断：フォームのエラーは静的テキストとして表示し、`aria-describedby`で入力に関連付ける。送信時のまとめ（エラーサマリー）はノティフィケーションバナー（error）で表示し、送信後にそこへフォーカスを移す。
- 理由：DADSインプットテキスト（アクセシビリティ）の規定。
- 代替案：`role="alert"`（読み上げの割り込みが起こる）。

## D-10トースト通知はDADSに該当コンポーネントがないため、ノティフィケーションバナーの縮小版として設計する

- 判断：画面右上（モバイルは下部）に固定表示、`role="status"`（`aria-live="polite"`）、success、error、infoの意味色、閉じるボタン付き、8秒で自動消去（ホバー・フォーカス中は停止）。
- 理由：操作完了の軽い通知は管理画面で必須。DADSのセマンティックカラーと「固定表示には閉じるボタンを必ず付ける」規定に従う。
- 代替案：すべてバナーで表示する（画面がうるさくなる）。

## D-11ツールチップ・ポップオーバー・コマンドパレット・スケルトン・タイムライン等はDADSにないためAPGに従って設計する

- 判断：WAI-ARIA Authoring Practicesのパターン（Tooltip、Dialog、Comboboxなど）に従い、見た目はDADSのトークン（枠線gray-420、elevation-1、角丸8px、フォーカスリング）で統一する。
- 理由：資料に記載がない部分はDADSの原則（アクセシビリティ、一貫性）から判断する。

## D-12データ可視化パレット

- 判断：ガイドブック「Blue」パレットから、白背景に対し3:1以上を満たす色を系列色に採用する。
  - 系列：1 = Blue 900 #0017c1、2 = Yellow 800 #a58000、3 = Blue 600 #3460fb、4 = Solid Gray 600 #666666、5 = Blue 1200 #000060
  - 単一色相（順序あり）：Blue 1200、900、600、400、200（400以下は3:1未満のため値ラベルを必ず併記）
  - 増減：増加Blue 600 #3460fb（文字はBlue 800 #0031d8）、減少Red 600 #fe3939（文字はRed 900 #ce0000）。矢印アイコンと符号を併記し色だけに依存しない
  - 目標・比較線：Solid Gray 800の破線、グリッド：Solid Gray 200、軸：Solid Gray 600
- 理由：色数を5色以内に抑え、色覚多様性（青、黄、グレーは識別しやすい）とコントラスト要件を両立する。

## D-13作業用の文書はGitに含めず、完了後に残す文書だけをコミットする

- 判断：作業中は`docs/*.md`を`.gitignore`の対象にした（利用者の指示）。完了後、作業用の文書（進捗`PROGRESS.md`、作り直し前の現状調査、DADSの調査メモ）は削除し、使う人の役に立つ文書（`docs/decisions.md`・`docs/tokens.md`・`docs/chart-guide.md`）だけをコミットする。
- 理由：進捗と調査メモは作業を再開するためのもので、完了後は内容がコードとREADMEに反映済み。判断記録・トークン一覧・グラフの選び方は、ソースコードのコメントから参照しており、テンプレートを改修するときにも使う。

## D-14ディレクトリ構成

```text
src/
├── tokens/            # デザイントークン（primitives / theme / typography）とコントラスト検査
├── components/
│   ├── ui/            # 汎用 UI 部品（1 コンポーネント = 1 ファイル + テスト）
│   └── charts/        # Recharts ラッパー
├── layouts/           # AppShell（サイドバー型）、TopNavLayout（上部ナビ型）
├── pages/             # ページ例（dashboard, applications, settings, auth, errors）
├── mocks/             # ダミーデータ
├── hooks/ lib/ context/ test/
```

- 理由：UI部品・グラフ・レイアウト・ページ・モックを分離し、テンプレート利用者が差し替える単位を明確にする。

## D-15デモはStorybookではなくアプリ内ページ（`/components/*`）で提供する（D-16で撤回）

- 判断：依存を増やさず、`src/demo/*.demo.tsx`に使用例を書き、`/components`配下のページで一覧表示する。E2E、axeの検査対象にもなる。
- 代替案：Storybook（依存が大きい）。

## D-16コンポーネントのデモページを廃止し、ページ例7画面をプレビューとする

- 判断：利用者の指示（「/componentsページはいらない。プレビューの7画面でいい」）により、`/components`と`src/demo/`を削除する。部品の使用例はページ例（ダッシュボード・一覧・詳細・フォーム・設定・ログイン・404/500）と単体テストで示す。E2Eのaxe検査は7画面と主要な操作状態（モーダル表示、フォームエラー、モバイル幅）を対象にする。
- 理由：利用者がテンプレートとして見るのはページ例であり、デモページは不要と判断された。
- 影響：タスクの完了条件3「各項目について、実装、デモ、単体テストがそろっている」の「デモ」は、利用者の指示によりページ例で代替する。PRの本文にも明記する。
- 代替案：デモページを開発者向けに残す（最初に提案したが、利用者が不要と判断）。

## D-17地（canvas）の上の文字色をDADSより1段濃くする

- 判断：`text-subtle`をgray-536 → gray-600、`error`をerror-1（red-800）→ error-2（red-900）、`warning`をyellow-900 → yellow-1000、`link-active`をorange-800 → orange-900にする。
- 理由：DADSの値は白背景で4.5:1を満たすが、管理画面の地（gray-50 #f2f2f2）の上では4.05〜4.33:1になり、実ブラウザーのaxeで違反になった。DADSは「セマンティックカラーは色相を保てば明度を調整してよい」としている。
- 代替案：地を白にする（面の区別がなくなる）。

## D-18アプリケーションシェルはページ全体でスクロールする

- 判断：本文だけを内側でスクロールさせる構造をやめ、ヘッダーとサイドバーをstickyにしてページ全体をスクロールさせる。
- 理由：内側スクロールでは、画面外の要素（読み上げ用の隠しテキストなど）にフォーカスが当たったときに画面全体がずれる不具合が起きた（利用者の指摘）。

## D-19グラフの目標線のラベルは凡例に出す

- 判断：参照線のラベルをグラフの中に描かず、凡例に「破線 + ラベル」として出す（`labelPosition`を指定したときだけグラフ内に描く）。
- 理由：グラフ内の文字は系列の線と重なりやすい。ガイドブックは凡例をグラフに隣接させることを推奨している。

## D-20作成フォームの操作ボタンは画面下部に固定しない

- 判断：ActionPanelのstickyを使わず、フォーム末尾に罫線で区切って置く。
- 理由：固定表示はフォームの上に浮いて見え、入力欄やサポートテキストを隠した（利用者の指摘）。

## D-21アイコン・チェックボックスなどは、隣の文字の1行目と上下中央でそろえる

- 判断：文字の横に置く部品（アイコン、チェックボックス、ラジオボタン、マーカー、表のチップ・操作ボタン）は、文字と同じ1行分の高さの枠（`h-lh`）の中で上下中央に置く。表の中では`TableCellLine`で包む。
- 理由：ベースライン合わせ + 固定のずらし量（`mt-0.5`など）では、部品の大きさや行の高さが違う場所で1〜3pxずれた（利用者の指摘）。この作りなら、文字が折り返しても1行目にそろう。
- 代替案：`items-center`で文字全体の中央にそろえる（複数行のとき1行目とずれる）。

## D-22ボタンの並びは、モバイルでもDOM順 = 見た目の順 = フォーカス順にする

- 判断：ダイアログの2つのボタンは、モバイルでも左がキャンセル・右が確定。ActionPanelとButtonGroupもCSSのorderや逆順（`flex-col-reverse`）を使わず、収まらないときだけ折り返す。
- 理由：モバイルで縦に積んで逆順にすると、幅がそろわず作りかけに見え（利用者の指摘）、見た目の順とフォーカス順も食い違う。

## D-23見た目の回帰テストは、PlaywrightのLinuxのイメージの中で撮る

- 判断：基準画像は、手元とCIの両方で`mcr.microsoft.com/playwright`のイメージの中で撮る（`scripts/visual.sh`）。差分の許容は0ピクセルにし、アンチエイリアスの揺れだけを`threshold`で許す。
- 理由：macOSとLinuxでは文字の描画が違い、同じ画面でも画像が変わる。同じイメージで撮れば、1pxのずれも見つけられる。チェックボックスの間隔を1px変えると、3つの画面で失敗することを確かめた。
- 代替案：OSごとに基準画像を持つ（画像の数が倍になり、手元で撮った画像をCIで使えない）。

## D-24画面はダミーのAPIを通してデータを読み書きし、読み込みの状態をuseQueryでそろえる

- 判断：画面から`src/mocks/`を直接読まず、`src/api/`の非同期の関数だけを使う。読み込みの状態は`useQuery`（キーごとに結果を保ち、画面を開いたときに裏で読み込み直す）で扱う。
- 理由：実際のAPIに置き換えるとき、差し替える場所を`src/api/`だけにできる。読み込み中、エラー、再読み込みの見せ方を、全画面でそろえられる。
- 代替案：TanStack Queryを使う（機能は多いが、依存が増える。テンプレートで要る機能は少ない）。

## D-25削除は確認ダイアログではなく、「元に戻す」で取り消せるようにする

- 判断：申請の削除は確認ダイアログを出さずにすぐ行い、トーストの「元に戻す」で取り消せるようにする。確認ダイアログは、取り消せない操作（アカウントの削除）と、ほかの人に影響する操作（承認の通知）だけに使う。
- 理由：DADSは、確認ダイアログだけを安全対策にしないよう求めている。確認を繰り返すと、利用者は読まずに押すようになる。
- 補足：操作の付いたトーストは自動では消さない（WCAG 2.2.1）。削除と同時にフォーカスを「元に戻す」へ移し、キーボードでもすぐ取り消せるようにする。

## D-26離脱の確認は、ルーターに一つのブロッカーで行う

- 判断：`useBlocker`は`UnsavedChangesProvider`に一つだけ置き、各フォームは`useUnsavedChangesWarning`で「変更がある」ことを登録する。
- 理由：react-routerのブロッカーはルーターに一つしか働かず、二つ目以降は無視される。設定の画面のようにフォームが複数あると、最後のフォームの確認しか出なかった。

## D-27強制カラーモードでは、背景色で表す状態をシステムカラーで描き直す

- 判断：`src/index.css`の`@media (forced-colors: active)`で、スイッチ、タブ、現在地の印、ステップを、システムカラー（`Highlight`など）で描き直す。チェックボックスとラジオボタンは、OSの標準の部品で描く。
- 理由：強制カラーモードでは背景色と影が消え、選択の状態が見分けられなかった。Tailwindのユーティリティより優先させるため、このスタイルはレイヤーの外に書く。

## D-28見本の画面は、スクリプトでまとめて消せるようにする

- 判断：見本の申請管理の画面とテンプレートの共通の部分を切り離し、`npm run remove-samples`で消せるようにする。CIの`starter`ジョブで、消したあとも検査とビルドとE2Eが通ることを毎回確かめる。
- 理由：テンプレートを使う人が最初にする作業を、手で探して消す作業にしないため。共通の部分が見本の画面に頼っていると、消したときに壊れることに気付けない。

## D-29画面の文言は、文言表を先に直してからコードに写す

- 判断：`docs/ui-text.md`に画面と要素ごとの文言を並べ、表記のルール（全角と半角の間に空白を入れない、1文のメッセージには句点を付けない、など）で点検してからコードに写す。
- 理由：画面ごとに書き方が揺れていた（「サンプル」「表示例」「見本」の混在、半角のコロン、受身形）。表で一覧にすると、揺れと違反を見つけやすい。

## D-30見本のメールアドレスと電話番号は、実在しないものにする

- 判断：メールアドレスはJPRSが予約している`example.jp`を使う。電話番号は`000-0000-`で始める。
- 理由：公開しているリポジトリの見本が、実在の組織や人に当たらないようにする。日本には、架空の用途に予約された電話番号がない。

## D-31ダークモードは、DADSのプリミティブから選んだ独自の配色にする

- 判断：`<html data-theme="dark">`のとき、`src/tokens/theme-dark.css`で色のセマンティック別名を上書きする。値は、DADSのプリミティブ（灰色、青、意味色の各段階）から選ぶ。配色は、設定画面の「表示」で「OSの設定に合わせる」「ライト」「ダーク」から選べ、既定はOSの設定に合わせる。
- 理由：DADSには、ダークモードの規定がない。部品はセマンティック別名で色を指定しているため、別名の値を差し替えれば、部品を直さずに配色を切り替えられる。プリミティブの範囲で選べば、トークン以外の色を書かない検査（`npm run lint`）も保てる。
- フォーカス：DADSの黒4pxの線は暗い地で見えないため、黄色4pxの線と黒2pxの帯に入れ替える。リンクとテキストボタンのフォーカスの黄色の塗りは、明るい文字が読めなくなるため、ダークモードでは塗らない。
- 検査：ライトと同じ組み合わせのコントラスト（`src/tokens/contrast.test.ts`）、全画面のaxe、見た目の回帰テストを、ダークモードでも行う。
- 代替案：ダークモードに対応しない（DADSの規定の範囲に留まれるが、暗い配色を望む利用者に応えられない）。DADSの段階にない色を足す（中間の灰色を使えるが、DADSのトークンだけで作るという方針が崩れる）。
